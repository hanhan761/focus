# 指标、记录与恢复约定

## 先测结果，再测工作流

为当前问题制定结果指标；下表是方法示例，数值要来自用户要求或实际基线。

| 任务 | 结果指标 | 验证证据 |
| --- | --- | --- |
| 软件故障 | 原始复现条件下症状消失；相关回归检查通过 | 输入、复现或测试命令、退出码、输出、提交或文件版本 |
| 性能问题 | 固定输入上的耗时或资源开销达到指定目标 | 环境、样本数、统计口径、基线与对照记录 |
| 算法实验 | 同一验证集上的主指标达到目标；预算满足约束 | 数据版本、配置、随机种子、日志、检查点 |
| 文稿或幻灯片 | 用户指定的事实、结构与版式检查项全部通过 | 当前文件版本、逐项清单、渲染或审阅记录 |
| 规则或工作流整理 | 当前动作无未裁决冲突；能定位唯一有效计划并接续 | 规则来源与适用路径、裁决、恢复探针 |

质量、成本和速度有取舍时，明确主指标与不能违反的约束。例如性能更快但准确性低于用户下限，仍不算通过。

## 默认过程指标

这些是本技能的运行约定，不是经实验证实的通用最优阈值。

| 指标 | 计算与口径 | 默认目标或触发条件 |
| --- | --- | --- |
| 已记录验证覆盖 | status=pass 且证据字段齐全的指标数 / 必要指标总数 | 验收时 100%；内容真实性须另行核对 |
| 动作对齐率 | 有效关联至少一个指标的工作流步骤数 / 工作流步骤总数 | 100%；缺失关联立即补目标或移入 parking |
| 当前执行步骤数 | workflow 中 doing 的数量 | 默认 1；不可把已有授权的协作误当失焦 |
| 待裁决冲突数 | conflicts 中 resolution 为空的条目数 | 当前动作相关冲突为 0 |
| 无证据连续周期 | 从 cycles 末尾向前数 new_evidence=false 的连续周期 | 未完成任务默认达到 2 就换方法并重新聚焦 |
| 无证据通过声明 | status=pass 但没有完整证据的指标数 | 0 |

覆盖率不是整体任务完成百分比：各指标工作量并不相等。无需加权生成“聚焦分数”，也不根据窗口大小推测上下文占用百分比。

## focus.json 是恢复摘要

已有计划时，plan_ref 指向它；不要在摘要中复制整套历史计划。只放当前主线及即将执行的短步骤，旧路线放 parking。完整原始日志留在用户项目原有位置，通过路径引用。

- schema_version 固定为 1。
- task_id 与 project_root 标识同一任务，恢复时对照实际工作路径。
- updated_at 是带时区的 ISO 时间；status 为 active、blocked 或 complete。blocked 是此文件对当前依赖的描述，不改变宿主的 goal 状态。
- objective 是结果目标；problem 是当前瓶颈，不是永久重写原始目标。
- instructions 保存当前有效约束的 source、scope、rule。保留适用的原始约束，详细内容用原文件链接，避免反复压缩丢失。
- conflicts 保存 sources 和 resolution；空 resolution 表示尚未裁决。只列当前主线相关项。
- metrics 每项有 id、name、baseline、target、current、check、status、evidence。status 为 pending、pass 或 fail。清单要求也可用字符串表示。
- workflow 每项有 id、action、metric_ids、status、output、check。status 为 todo、doing 或 done。check 包含验证动作与预期结果。
- cycles 每项有 step_id、action、result、new_evidence、evidence。真正的新证据才标 true；失败实验可以给出新证据。引用的步骤保留到对应周期移入原项目日志之后。
- evidence 是对象列表，每项有 source、revision、observation。source 指文件、日志或结果位置；revision 标识提交、文件哈希、数据版本或对应的输入与检查时间；observation 写实际观察。含字段不代表检查器证明其为真。
- checkpoint 保存 last_verified_action、artifacts 与 next_action。每个 artifact 有 path、revision、summary；初始暂无产物时列表可为空。下一步必须具体；已完成时写明确终态。
- decisions 和 parking 是短字符串列表，分别保存裁决理由和暂缓想法。

unknown 适用于未测的 baseline/current；pass 时 current 必须为实际结果。输入或产物版本变化后重新验证相关项，不强行重跑无关已通过检查。

模板可直接作为起点，适当删去示例内容并填入任务事实。项目绝对路径、任务 ID 和指标不是脚本替用户决定的。

## 检查器退出码

| 退出码 | 含义 |
| --- | --- |
| 0 | 结构有效且记录中未触发纠偏；带 --complete 时还通过记录层面的验收门槛 |
| 1 | 应纠偏：冲突、动作不对齐、多项 doing、无证据通过声明或无证据连续周期 |
| 2 | 文件或结构错误，先修复记录 |
| 3 | --complete 的验收条件尚未满足；保留未完成要求继续工作 |

--json 输出便于机器读取；不带该参数打印紧凑报告。--stall-limit 可覆盖默认的 2，必须为正整数。检查器是只读工具，不执行 evidence 中的内容，不抓取链接，不声称任务实际成功。

## 恢复探针

在交接、压缩后或再次说“聚焦”时，不依赖旧聊天，仅用检查点、适用规则及证据回答：

1. 用户真正要的结果是什么？后续消息改变了哪些要求？
2. 当前瓶颈是什么，来源证据在哪？
3. 哪些产物已验证，属于哪个输入与版本？
4. 哪些约束仍有效，冲突由谁的什么指令裁决？
5. 还有哪些必要指标未通过，哪些已做工作无需重复？
6. 接下来唯一的具体动作是什么，它验证哪个指标？

每项核对原始依据，答不出就补对应事实。6/6 是人工恢复检查的目标；字段非空或摘要字数不构成通过。

## 聚焦卡示例

> 当前问题：性能实验反复换模型，尚无同一验证集的对照结果。
>
> 主因：三份实验计划都称自己为当前方案；证据是实际计划文件与配置差异。
>
> 目标：在固定数据与预算内，确认一个可复现的改进方案。
>
> 指标：固定验证集主指标达到用户目标；耗时不超过预算；所有对照输入一致。
>
> 工作流：确认数据与配置 → 测基线 → 只改一个变量 → 同口径对照 → 验证并记录。
>
> 下一步：核对验证集哈希和当前运行配置，建立可比较的基线记录。

实际输出附当前值、目标值与证据位置。不能照抄这个例子的目标或阈值。
